# Архитектура

## Компоненты

| Компонент | Ответственность |
| --- | --- |
| React, TypeScript, Vite | Интерфейс студии. React Router связывает разделы и отдельные карточки |
| TanStack Query | Запросы, повторная загрузка изменившихся данных и состояние интерфейса |
| Workers со Static Assets | Публикация собранного интерфейса и маршрутизация REST API под `/api/` на одном домене |
| Cloudflare D1 | Рубрики, публикации, идеи, связи с медиа, настройки, журнал и метаданные |
| Cloudflare R2 | Оригинальные файлы и отдельные превью |
| Wrangler | Локальный Worker с эмулированными D1 и R2, миграции и будущая сборка для Cloudflare |
| Node.js CLI | Поэтапное резервирование и восстановление крупных коллекций |

`src/` содержит интерфейс и общие клиентские функции. `worker/` содержит API и бизнес-правила. `database/migrations/` хранит версионированную схему, `database/seeds/` содержит стартовое наполнение. `public/` содержит ресурсы интерфейса и PWA. `tests/` и `scripts/` содержат сценарии проверки и обслуживания.

## Согласованность на нескольких устройствах

Серверные записи являются источником данных. Клиент обновляет открытые списки каждые пять секунд и при возврате на вкладку, а после записи помечает связанные запросы для обновления. Подключённое устройство должно увидеть изменения при следующем успешном запросе. Браузер приостановленной вкладки может выполнять запросы реже.

При сохранении карточки клиент передаёт увиденную им версию записи. Запись обновляется с проверкой версии. При устаревшей версии сервер возвращает `409 Conflict`. Интерфейс сообщает о конфликте. Перед повторным редактированием сохраните свой текст отдельно, перечитайте карточку и перенесите нужные правки.

Оригиналы и связи с ними хранятся отдельно. При дублировании меняются связи в базе. После удаления связи физическое удаление объекта возможно только тогда, когда он больше не нужен другим материалам и соблюдены условия очистки.

## Основные группы REST API

| Группа | Маршруты |
| --- | --- |
| Рубрики, публикации, идеи | `/api/categories`, `/api/publications`, `/api/ideas` |
| Поиск, статистика, история | `/api/search`, `/api/stats`, `/api/activity` |
| Планирование | `/api/calendar` и поле даты в карточке публикации |
| Файлы | `/api/uploads`, `/api/media`, `/api/attachments` |
| Статусы, конфигурация | `/api/statuses`, `/api/custom-fields`, `/api/settings` |
| Корзина, архив, диагностика | `/api/trash`, `/api/system`, `/api/system/archive` |
| Резервные копии | `/api/backups`, `/api/export`, `/api/import` |

Списки публикаций и идей поддерживают пагинацию. Поиск, фильтры и сортировка выполняются в серверном слое. Проверки внешних связей и параметризованный SQL дополняют ограничения в схеме D1.

## Размещение и перенос

Студия обращается к REST API по относительным адресам. Пакет Vite обслуживается вместе с Worker, поэтому браузеру не требуется внешний CDN для кода интерфейса. Стабильные маршруты API, идентификаторы объектов, формат экспорта и схема SQLite упрощают перенос.

При смене только объектного хранилища нужно реализовать серверный адаптер под выбранный S3-совместимый сервис, включая multipart и Range, перенести объекты с сохранением идентификаторов и проверить SHA-256. При смене всего провайдера также потребуется адаптация серверной среды и базы. Адаптеры Cloudflare используют специфичные привязки R2 и D1. Приложение не переключается на другой сервер автоматически.

## Модель доступа

У любого человека, открывшего адрес, одинаковые права. Проверки запроса, ограничение частоты, лимиты и подтверждения уменьшают вероятность случайной ошибки и нагрузку от однотипных запросов. Они не позволяют установить, кто изменил запись, и не останавливают целенаправленное изменение данных по известному адресу. Настройки студии тоже доступны на запись. Серверные ограничения, задаваемые конфигурацией размещения, действуют отдельно от интерфейса.

Сайт использует POST, PATCH и DELETE для записи, проверяет происхождение браузерных запросов и отдаёт файлы через API. R2 хранится закрытым. Учётные данные облака нужны только при обслуживании инфраструктуры и внешнем резервировании. Технический журнал используется для диагностики и истории событий, а не для атрибуции действий людям.
